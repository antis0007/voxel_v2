# Atmosphere Runtime Plan

## Objective

Promote the current atmosphere runtime from "owned placeholder textures" to "real runtime-generated atmosphere products" so sky, aerial perspective, terrain fog coloration, and cloud lighting start depending on explicit runtime products instead of shader-local approximations.

This checkpoint keeps the analytic path only as an explicit fallback mode.

## Current Gaps

The current renderer already has the correct owner module in `src/render/atmosphere.rs`, but it still has three major gaps:

1. Sky-view and multiscatter are seeded on the CPU instead of generated by runtime passes.
2. Aerial perspective is still shader-local analytic math instead of a runtime-owned product.
3. Terrain and cloud lighting still depend too heavily on `LightingState` sky/fog heuristics instead of atmosphere outputs.

## Required Outcomes

- `AtmosphereParameters` exists as an explicit input block decoupled from `LightingState`.
- Transmittance, multiscatter, sky-view, and aerial perspective are explicit runtime-owned products.
- Sky-view and multiscatter are generated by real runtime passes.
- Terrain fog target color moves onto atmosphere products.
- Cloud lighting consumes atmosphere products where practical.
- Analytic atmosphere remains available only as an explicit fallback mode.
- Debug views exist for transmittance, sky-view, multiscatter, and aerial perspective.

## Design Principles

- The atmosphere runtime owns products and update policy.
- `LightingState` should not remain the source of final sky appearance.
- Terrain and clouds sample atmosphere data; they do not fork atmosphere logic.
- Camera motion should invalidate only view-dependent products.
- Constant atmosphere composition changes should invalidate constant LUTs.
- Fallback paths must stay explicit and nameable.

## Target Owner Types

Expand `render::atmosphere` around three explicit layers:

### `AtmosphereParameters`

CPU-facing atmospheric input state.

This should contain physical or authoring-facing inputs such as:

- planet or ground radius abstraction
- atmosphere height
- Rayleigh scattering coefficients
- Mie scattering/extinction coefficients
- absorption coefficients if introduced
- Rayleigh and Mie scale heights
- ground albedo
- sun illuminance / spectral scale
- optional artistic scale multipliers that are still clearly atmosphere parameters

During transition, it is acceptable to construct this from current time-of-day or lighting data through a compatibility adapter, but the compatibility layer must not be the long-term owner.

### `AtmosphereProducts`

Runtime-generated textures and views:

- transmittance LUT
- multiscatter LUT
- sky-view LUT
- aerial perspective volume

### `AtmosphereLightingProducts`

Small derived lighting data that is genuinely lighting and worth sharing:

- sun transmittance at ground
- sun transmittance at representative cloud altitudes
- low-order ambient sky probes or directional ambient samples
- optional fog scaling factors derived from atmosphere, not hand-authored gradients

This belongs to the atmosphere runtime, not to `LightingState`.

## Product Set

Recommended initial product set:

### Transmittance LUT

- dimension: `2D`
- initial size: `256 x 64`
- format: `rgba16float` or `rgba32float` if precision proves necessary
- invalidation: atmosphere parameter changes only

### Multiscatter LUT

- dimension: `2D`
- initial size: `32 x 32`
- format: `rgba16float`
- invalidation: atmosphere parameter changes, plus any sun-illuminance dependency if folded in

### Sky-View LUT

- dimension: `2D`
- initial size: `192 x 108` or `256 x 128`
- format: `rgba16float`
- invalidation: camera orientation, camera altitude band, sun direction, and any constant-LUT dependency changes

### Aerial Perspective Volume

- dimension: `3D` or `2D array` slices; prefer one explicit volume owner
- initial size target: `32 x 32 x 24`
- format: `rgba16float`

Recommended content:

- RGB: in-scattered radiance toward the camera from the froxel center
- A: transmittance from the camera to the froxel center

Invalidation:

- camera matrices
- camera altitude / view volume
- sun direction
- atmosphere parameter changes

This product is required to stop terrain and clouds from computing their own atmosphere segment heuristics.

## Pass Graph

The generation order should be explicit:

1. transmittance
2. multiscatter
3. sky-view
4. aerial perspective
5. optional small derived-lighting reduction pass

Recommended implementation path:

- use compute passes for all product generation
- keep generation before shadow/world/cloud rendering
- cache constant products aggressively
- regenerate view-dependent products only when needed

This should happen during per-frame renderer preparation, not during the sky pass.

## Invalidation Rules

Use explicit dirty flags, not implicit "recompute everything" behavior.

Suggested invalidation groups:

### Constant Product Dirty

Invalidates:

- transmittance
- multiscatter
- all dependent dynamic products

Triggers:

- `AtmosphereParameters` change

### Sky Product Dirty

Invalidates:

- sky-view
- aerial perspective
- derived lighting probes if based on sky-view

Triggers:

- camera orientation change beyond threshold
- camera altitude band change
- sun direction change
- constant product dirty

### Aerial Perspective Dirty

Invalidates:

- aerial perspective volume

Triggers:

- camera matrices change
- camera altitude/view range change
- sun direction change
- sky product dirty

## Binding Model

Keep a dedicated atmosphere bind group, but expand it to match the real product set.

Recommended contents:

- uniform buffer for runtime mode/debug/product dimensions
- buffer for `AtmosphereParameters`
- transmittance texture
- multiscatter texture
- sky-view texture
- aerial perspective texture
- optional derived-lighting uniform/storage buffer

The exact binding count can be tuned, but the atmosphere runtime should remain a self-contained bind group owner.

## Shader Migration Plan

### `atmosphere_shared.wgsl`

Convert this file from "mostly analytic atmosphere implementation" toward:

- sampling helpers for runtime products
- product-space UV helpers
- explicit analytic fallback helpers

The runtime product path should become the primary path. The analytic path should remain behind a named mode gate.

### `world_shader.wgsl`

Target changes:

- replace fog target color heuristics with aerial perspective sampling
- replace hand-authored ambient sky gradient logic with atmosphere-derived lighting or sky-view sampling
- keep only direct-light and material response logic in terrain shading

The world shader should stop combining `light.sky_top_saturation`, `light.sky_horizon_reserved`, and `light.fog_color_density` as the final active atmosphere model once runtime products are ready.

### `cloud_shader.wgsl`

Target changes:

- use runtime sun transmittance for cloud-altitude lighting
- use runtime multiscatter or atmosphere-derived ambient products for cloud ambient lighting
- use runtime aerial perspective for cloud-to-camera atmospheric segment

Clouds can continue using current procedural density for now, but they should stop inventing atmosphere terms locally where a runtime product exists.

### `sky_shader.wgsl`

The sky pass should sample the sky-view product and any needed atmosphere lighting support data. It must not reacquire cloud composition responsibility.

## Atmosphere-Derived Lighting Products

Some atmosphere outputs are genuinely shared lighting data and should not be recomputed independently in each shader.

Recommended first derived buffer:

- ground-level sun transmittance
- low-cloud sun transmittance
- mid-cloud sun transmittance
- high-cloud sun transmittance
- zenith ambient probe
- sun-side horizon ambient probe
- cross-sun horizon ambient probe
- anti-sun horizon ambient probe

This is acceptable shared lighting data. It should live in the atmosphere runtime, not inside `LightingState`.

## Aerial Perspective Usage

### Terrain

For opaque terrain:

- sample aerial perspective using view direction and linear eye depth
- use the returned transmittance and in-scatter to replace the current fog target-color heuristic

### Clouds

For volumetric clouds:

- apply the same atmospheric product for cloud-to-camera extinction/in-scatter
- ensure the cloud pass and terrain pass agree on atmospheric color at sunrise, sunset, and overcast conditions

### Debug

The aerial perspective product must be inspectable directly.

Recommended debug representation:

- a slice atlas view for the whole volume
- or a single "applied aerial perspective" view sampled in screen space

If only one debug mode is added first, prefer a slice atlas because it proves the runtime product exists independently of the final shading path.

## Recommended Resolutions and Formats

Start conservative. Correct ownership matters more than the first perfect resolution.

Recommended starting point:

- transmittance: `256 x 64`, `rgba16float`
- multiscatter: `32 x 32`, `rgba16float`
- sky-view: `192 x 108`, `rgba16float`
- aerial perspective: `32 x 32 x 24`, `rgba16float`

Only promote precision or resolution when a measured artifact justifies it.

## Implementation Stages

### Stage 1: Parameter Separation

- introduce explicit `AtmosphereParameters`
- keep a compatibility adapter from `LightingState`
- make invalidation rules explicit

### Stage 2: Real Constant LUT Passes

- replace placeholder seeding for transmittance/multiscatter with generation passes
- keep existing debug routes alive

### Stage 3: Real Dynamic LUT Passes

- replace placeholder sky-view generation
- add aerial perspective volume generation

### Stage 4: Shader Migration

- move terrain fog target color to aerial perspective
- move cloud sun transmittance and ambient inputs to runtime products
- reduce dependency on `LightingState` sky gradients

### Stage 5: Cleanup

- isolate analytic fallback as a clearly labeled mode
- remove dead placeholder generation paths

## Validation Checklist

Visual validation must confirm:

- sunrise and sunset color coherence improves across sky, terrain, and clouds
- overcast scenes shift toward consistent cooler/neutral atmosphere lighting
- terrain haze color matches the sky instead of looking separately graded
- cloud-to-camera haze matches terrain haze

Structural validation must confirm:

- runtime products are generated by passes, not CPU-seeded placeholders
- atmosphere debug surfaces show the actual products
- atmosphere ownership stays in `render::atmosphere`
- `LightingState` does not gain more atmosphere policy

## Deferred Work

This checkpoint does not attempt:

- final production-ready planet/space-view fidelity
- volumetric shadowing through the atmosphere
- cloud storage rewrite
- unified volumetric media for precipitation, dust, and fog

It is specifically the ownership and runtime-product checkpoint.
