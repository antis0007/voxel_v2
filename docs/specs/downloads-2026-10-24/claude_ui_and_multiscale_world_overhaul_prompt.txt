These are test values, not rigid physical-pixel rules. Use the toolkit's coordinate/DPI model consistently and test actual on-screen readability.

Scaling:

Component states:

Feedback:

Safe areas:
Anchor HUD to margins and respect configured scale/aspect ratio. Tooltips and context menus clamp/reflow inside the viewport. Tooltips must not cover the object/action the player is trying to inspect unnecessarily.

05. EXPLORATION AND COMBAT HUD

Build a compact default HUD with a clear information hierarchy:
- Bottom center: the action hotbar, with a strong selected-slot outline and small binding hints.
- Near the hotbar: health and the currently relevant resource, compact and consistent.
- Center: a subtle adaptive crosshair or targeting cue.
- Context area near the center/lower center: a concise interaction prompt when something actionable is targeted.
- Peripheral area: short-lived pickup/status notifications, stacked with a cap.

Hotbar:
Preserve actual slot count and saved bindings. If the existing game has no established count, begin by testing nine slots; do not shrink a larger existing hotbar and lose assignments. Show item count, durability/charge only when relevant, and a distinct selected item. Avoid repeating the selected item's full name permanently; show it briefly on selection or when needed.

Resources:
Health is always understandable. Mana/energy/stamina appear according to actual mechanics. Do not display invented bars. Support configurable numeric values. Segment/pip styling is acceptable if it maps clearly to quantities and remains legible at large capacities. Critical changes have clear feedback without filling the screen with warnings.

Target inspection:
Show a short object name and action, such as a real machine's name and current binding for Open. Material/quantity/voxel-size detail appears in building/inspection mode or through an additional held modifier, not permanent multiline debug text.

Status effects:
Use a capped compact row with duration/stack information on inspection. Prioritize dangerous/important effects. Avoid covering health/hotbar with repeated notifications.

Combat:
Telegraphs, crosshair feedback and essential resources remain visible during effects. Enemy bars should appear where useful, with restrained name/detail density. Do not reveal hidden enemy information unintentionally. Keep the central aim region clear.

Debug:
Move engine diagnostics into a dedicated toggleable overlay and developer screens. Use configurable bindings. Do not assume a particular key is free. Diagnostics remain available without becoming the normal game aesthetic.

06. INVENTORY AND CONTAINER INTERACTION

Use a compact consistent inventory grid with strong item silhouettes, readable stack counts and clear selection. Provide a stable header, category/search controls when needed, and a context/details area.

Layout:
Player inventory plus equipped/active items in a clear grouping. When opening a container, show its grid alongside the player's with consistent slot styling and transfer direction. Avoid moving frequently used controls unpredictably between screens.

Interactions:
Primary click select/pick up/place; supported quick-transfer modifier; split stack; move one; swap compatible items; keyboard navigation; context actions for equip/use/inspect/drop where valid. Map these to existing controls and make bindings discoverable. Preserve existing useful behavior rather than arbitrarily renaming every control.

Drag behavior:
Show the dragged item, quantity and valid/invalid destination. Use clear pending/committed state. Failed drops return safely without losing or duplicating items. Closing a menu while holding a stack must deterministically restore/commit it according to a defined rule. If the source is occupied, choose a safe available destination or keep a recoverable state; do not silently drop items into the world.

Transfers:
Use authoritative inventory commands with capacity and compatibility checks. Splits, swaps, quick-transfer and auto-stack preserve quantities and metadata. Sorting is scoped to the selected container, has a stable deterministic order and does not rearrange equipped/hotbar items unless explicitly chosen. Avoid destructive surprises.

Search/filter:
Match names and useful categories/tags with clear empty results. Filters change presentation, not item ownership. Keep selections stable when items move or counts change. Large inventories need efficient rendering/querying, not per-frame expensive rebuilding of all metadata.

Tooltips:
Name, concise purpose, relevant stats, state, and action hints. Advanced properties are expandable/held-detail. Compare equipment with clear deltas. Avoid walls of repeated flavor text before useful information.

Accessibility:
Important categories differ by shape/text as well as color. Support larger labels and keyboard operation. Touch/controller behavior is only required if supported or part of the current platform scope; do not claim support without implementing focus/navigation.

08. WAND AND SPELL EDITOR

This is a signature interface. Make ordering, capacity, timing and interactions understandable while preserving the real spell model.

Layout:
Selected wand/model/icon and concise actual stats; ordered spell/modifier slots; available spell inventory; a focused description/preview area. Show slot order unambiguously and keep drag/reorder feedback clear.

Stats:
Only display actual implemented properties: for example capacity, resource cost, cast delay, recharge or other existing values. Explain units and whether a value belongs to the wand, a spell or the resulting sequence. Do not import a named game's exact stat model if this engine differs.

Relationships:
Represent supported modifiers, triggers, payloads or grouping with clear connectors/indentation/brackets. The UI must reflect the runtime interpretation. Invalid configurations explain the failing rule and highlight the relevant slot; they are not merely red with no explanation.

Preview:

Editing:
Reordering preserves spell identity and quantity. Changing selection cannot silently discard pending edits. Define apply/immediate-commit semantics and use them consistently. If runtime rules restrict editing while casting/in combat, explain the actual rule.

Tooltips:
Short effect explanation first, then real cost/timing/compatibility. Show meaningful combined consequences for the selected build. Keep flavor text secondary. Provide a quick way to compare wands without opening multiple layered popups.

Undo:

Machine panel:

Units:

Process view:

Circuits:

World overlay:

Accessibility:

12. UI STATE, INPUT ROUTING AND GAMEPLAY OWNERSHIP

UI renders state and requests actions; gameplay owns inventories, equipment, crafting, spells, machines and world edits. Do not duplicate simulation rules inside widgets.

Define clear interaction states: normal play, focused panel, dragging item, text entry, rebinding and modal confirmation where actually required. Manage cursor capture/visibility intentionally. Input should be consumed by the correct layer once. Prevent movement/fire/build commands while typing or interacting with panels according to existing pause/network rules.

Escape/back:
Close the most immediate popup/drag/modal safely, then the panel, then pause according to a consistent hierarchy. Never lose held items or apply an unintended world action during closure. Focus returns to a sensible control.

Stable identity:
Use item/container/recipe/machine IDs rather than transient row indices for actions. Sorting, filtering, quantity updates and asynchronous state must not retarget a click to a different object. Use revisions/validation when needed.

Persistence:
Save relevant preferences, filters or selected tabs only when useful; do not persist invalid transient pointers. World state remains authoritative. If multiplayer/networking exists, handle pending/failed actions without assuming local prediction succeeded. Do not invent a networking requirement if the game is local-only.

Implementation:
Use the current toolkit's strengths. Centralize reusable slot, tooltip, button, status, progress, quantity and panel components. Avoid a new UI framework migration unless a concrete blocker is proven. Keep debug tooling available in its own layer.

14. EXPLICIT SCALE HIERARCHY FOR WORLD GENERATION

Separate three concepts:
A. World-design scale: region, landform, habitat, structure, plant, detail.
B. Physical voxel resolution: authoritative editable material/occupancy granularity.
C. Render LOD: visual simplification chosen for distance and projected importance.
These are related but not interchangeable. Render LOD must not change inventory yields, terrain ownership or the meaning of a stored edit.

World-design hierarchy:
1. Region: ridge networks, basins, watershed connections and broad climate/exposure.
2. Landform: valley floor, lake basin, gorge, cliff, hill shoulder and major cave system.
3. Habitat/settlement patch: forest stand, meadow, wetland, quarry, town district and ruin envelope.
4. Landmark/object: tree, boulder formation, building, bridge, dungeon room and stream reach.
5. Local geometry: roots, banks, arches, stairs, rock strata, soil layers and medium vegetation.
6. Fine detail: selected bark shapes, stone trim, small plants, material grain and supported fine edits.

For every layer define:
Inputs/owner; deterministic identity; bounds/dependency radius; output representation; what can change at runtime; persistence; and how lower/higher representations derive from it.

Do not evaluate all layers independently with unrelated noise. A large root belongs to a tree, a tree belongs to a stand, the stand responds to soil/slope/water, and those respond to the region landform. Small detail reinforces this hierarchy.

15. REGION, TERRAIN AND HYDROLOGY GENERATION

Begin with a connected bounded test region using existing streaming, rather than promising an infinite globally coherent watershed from a local noise function.

Plan major ridges, basin floors, drainage/outlets and landmark opportunities. Build directional ridges with varying peaks/shoulders and subordinate spurs. Use different valley cross-sections for open basin and narrow gorge. Add bounded local roughness only after main forms work.

Water:
Give lakes persistent identities, levels and outlet policies. River reaches have connected paths, widths and surface profiles. Ordinary downstream profiles do not rise unexpectedly; waterfalls/steps are explicit. Validate confluences and lake/river transitions. Keep caves near water intentionally dry/flooded/connected according to the real fluid model.

Cross-region contracts:
If extending beyond the initial region, establish shared ownership for drainage ports, ridge continuation and crossing features. Adjacent regions consume the same boundary data. Do not independently invent incompatible rivers at each chunk edge.

Terrain layers:
Bedrock/strata, soil and surface cover derive from geology and depth. Excavation reveals coherent materials. Caves/overhangs use the actual volumetric representation where required. A heightfield may support ordinary far hills but cannot alone describe caves, arches or cliff housing.

Landform quality:
Avoid equal-sized conical peaks, evenly terraced beaches and noisy bumps on every face. Use large quiet surfaces where the reference calls for them. Terrain should offer interesting traversal and useful building space, not constant collision clutter.

Landmarks:
Place them using hard support/access/water constraints before artistic scoring. Score silhouette, plausible route views and spacing only after validity passes. Use bounded candidate search and clear failure/fallback behavior.

16. HABITATS, TREES, STRUCTURES AND FINE DETAIL

Habitat patches:
Use moisture, exposure, slope, soil and canopy conditions plus controlled clustering. Keep ecological transitions between biomes. Sharp cliffs/banks can remain crisp while vegetation and atmospheric contributions change gradually.

Vegetation:
Use species/age archetypes with trunk taper, meaningful branch structure, roots, connected crown lobes and gaps. Generate stands with edge/interior/clearing structure. Keep some suppressed young trees, deadwood and varied age where appropriate. Do not replace one generic tree with dozens of random recolors.

Ground cover:
Patch grass, litter, moss, flowers and shrubs according to habitat. Keep routes, machinery spaces and player-built surfaces clear. Fine decorative plants need not have individual physics/collision. Harvestable or structurally important organisms retain stable identity and persistent state.

Shorelines:
Distinguish protected sand, raised soil/root bank, embedded rock projection and low wet reed margin. Align wetness/vegetation to actual water state. Preserve open water as compositional space.

Structures:
Plan masses, circulation, foundations, floors/openings and roofs before ornament. Generate interiors that correspond to visible exteriors. Dungeon lighting and actual route accessibility are part of generation validation. Historical damage derives from intact architecture; rubble has plausible material/placement and does not seal every route.

Fine voxel detail:
Use finer geometry selectively around visible silhouettes, roots, arch profiles, stair/landing edges, important mechanisms, sculptures and close interactive features. Large quiet walls/hills do not need the same density. Material patterns may carry shallow detail where actual geometry would add little value, but cannot fake traversable openings or meaningful relief.

Artistic color:
Use macro/medium material variation with restrained fine grain. Keep stone, soil, bark, plaster, metal and water distinct. Avoid arbitrary high-contrast patches on every voxel. Preserve broad light/value grouping at all representations.

17. PHYSICAL VOXEL RESOLUTION: REQUIRED INVARIANTS

Audit the actual data model first. If the world has fixed authoritative resolution and multiple visual LODs, report that accurately. Do not advertise arbitrary physical subdivision through a UI control that only changes the mesh. If variable resolution exists, document its constraints and extend it carefully.

Required invariants for any supported physical scales:
- One authoritative material/occupancy result at any world location.
- Shared boundaries have consistent ownership and coordinates.
- Subdivision preserves parent content/state unless an explicit edit changes it.
- Coarsening/compaction never silently deletes meaningful fine edits or mixes materials into a different gameplay result.
- Raycasts, collision, rendering and edit previews refer to compatible world geometry.
- Resource accounting follows the actual physical/material policy across scales.
- Stable feature/loot IDs prevent subdivision from rerolling resources or duplicating rewards.
- Save/load retains all fine edits and the information required to interpret their coordinates/version.

Coordinate rules:
Use the existing canonical world-coordinate scheme. Specify quantization, negative-coordinate behavior, cell intervals, boundary tie-breaking and supported scale ratios. Avoid independent floating-point rounding in rendering, physics and placement. Test negative positions and far coordinates explicitly.

Subdivision:
If a coarse cell is refined, derive child state deterministically from the authoritative source/edits. Do not simply rerun a different generator seed at finer scale. Preserve metadata and removed/harvested content. Uniform regions may compress efficiently without allocating every fine cell.

Coarsening:
Distinguish visual aggregation from physical state compaction. A mixed or edited area may remain stored at finer detail while rendering a coarse approximation. Never overwrite detailed stored state merely because the player walked away. Use conservative feature preservation where a coarse proxy cannot express a hole, thin wall or bridge.

Sampling:
Fine surface detail can be omitted visually at distance, but the major surface, important apertures and edited silhouette must remain coherent. Small noise layers should not cause a mountain to change shape radically when approaching it.

Material cost/yield:
Document how volume maps to item units and how rounding/remainders work. Use sufficient exact/consistent accounting for supported scales. Repeated refine/place/remove/coarsen cycles must not generate free material or destroy large amounts through repeated rounding. If the game intentionally uses discrete block-item rules, preserve and communicate those rules instead of pretending everything is continuous volume.

Implementation scope:
Do not rebuild storage into an octree or another architecture merely because multiscale detail sounds desirable. Improve artistic generation at all existing supported scales first. Add physical-resolution capabilities only where necessary and supported by a concrete integration plan with persistence/collision tests.

18. RENDER LOD, STREAMING AND EDIT CONSISTENCY

Derive near/middle/far representations from the same region, feature and edit state.

Preservation priority:
Terrain ridge/valley form before tiny bumps; tree canopy/major branches before leaf detail; architecture roof/tower/arch shape before trim; important edited holes before surface grain; habitat color/coverage before individual small plants.

Boundaries:
Use the actual mesher's suitable seam/transition method. Shared input alone does not prove matching output: inspect boundary vertices, normals, material summaries and collision where relevant. Do not invent a specific stitching algorithm before auditing the existing topology.

Coverage:
Maintain an old valid representation until a replacement is ready. Avoid holes during loading. Non-heightfield structures such as bridges/arches/overhangs need suitable proxies. A far heightfield cannot be the only fallback for an edited underground entrance or suspended root bridge.

Interaction:
If a coarse visual proxy is insufficient for accurate picking/editing, resolve the authoritative target before committing. Show an honest pending/limited preview rather than editing a guessed cell. Do not make a distant visible resource harvestable repeatedly without loading its persistent state.

Async jobs:
Capture source revisions and reject stale results. A tree removed during meshing must not reappear. Propagate dirty bounds to dependent meshes, collision, lighting, navigation and far proxies. Bound/cancel obsolete work during rapid travel.

Save/version:
Keep existing worlds compatible or implement explicit migrations. Retain generator identity where needed. UI preferences can migrate independently from terrain generation; do not reset an entire world to update interface styling.

19. SHARED UI/WORLD PLAYTESTS

Validate the two overhauls together through complete actions:

A. Explore the improved shore with the new HUD. Identify a tree/rock, collect materials, receive compact feedback, open inventory, split/transfer a stack and resume play without accidental firing or placement.

B. Build a small shelter/workshop at more than one supported placement scale. Preview bounds/cost, rotate/snap, place/remove, verify material accounting, save/reload and inspect from near and far. The UI explains scale without exposing internal rendering details.

C. Enter a newly improved ruin/dungeon. Read the route and enemy cues, change equipment/wand configuration safely, inspect an item, operate a mechanism and return to gameplay. No panel/effect obscures essential combat information.

D. Craft a real item, including insufficient-resource and output-full cases. Feed a machine, inspect its actual blocking state, fix the problem and observe real progress/output. UI numbers and authoritative simulation agree.

E. Travel from a valley/settlement toward a distant landmark. Major geometry and biome identity remain consistent; the HUD is quiet; discovery feedback is useful; fine details appear without distracting shape changes.

F. Change UI scale/graphics quality and repeat the critical interactions. Preserve legibility, input/focus, geometry meaning and gameplay cues.

These are acceptance scenarios, not permission to fabricate unsupported crafting, fluid, wand or circuit mechanics. Use existing systems, implement necessary focused gaps, and clearly report genuinely absent features.

20. PERFORMANCE, ASSETS AND IMPLEMENTATION DISCIPLINE

Reuse current rendering/UI facilities. Centralize icon atlases, fonts, shared components and formatting. Avoid loading textures/fonts per frame, rebuilding all recipe graphs on hover, allocating huge strings each tick or scanning the entire world for a target tooltip.

UI updates:
Use stable state, cached derived views and appropriate invalidation. Render only relevant visible content. Keep the current immediate/retained-mode architecture if it works; this task is not an excuse for a framework migration.

World work:
Cache coarse plans and spatial indexes. Query local intersecting features. Bound generation, placement attempts, physics activation, light counts and upload queues. Use finer detail where it adds visible value. Preserve gameplay state when reducing decorative cost.

Measurements:
Record hardware, resolution, UI scale, graphics settings, seed/build and route. Track CPU/GPU times where available, frame-time p50/p95/p99, memory, generation latency and upload spikes. A 60 fps target has a 16.67 ms frame interval; higher targets require a correspondingly smaller whole-frame budget. Measure actual headroom before assigning costs.

Check menu-open overhead and world traversal separately. A beautiful inventory should not trigger a major scene stall, and closing it should not force an unnecessary world rebuild. Do not claim performance on untested hardware.

Assets:
Produce coherent original icons/panels/font usage and maintain provenance/licenses. Temporary placeholders are explicitly marked and replaced before visual completion. Do not ship copied named-game assets or use generated concept screenshots as evidence of engine implementation.

- Remove a tree or tower while a mesh/proxy job is pending; reject obsolete output.
- Verify connected water/terrain/structure boundaries and valid routes after generation.
- Preserve player-built surfaces, harvest state, machine contents and container rewards on reload.
